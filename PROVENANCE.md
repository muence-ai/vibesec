# Provenance

How VibeSec v1.0.0 was produced, and what that means if you want to train on it.

## Applications are machine-generated

Every application in this benchmark was generated by a language model from a short feature
request (kept in each task's `seed_prompt`). **No task is derived from a production
repository, an open-source project, or any human-authored codebase.** There is no upstream
project whose license needs to carry through.

That is a deliberate trade:

- **Upside** — no licensing ambiguity, no leakage of anyone's private code, and tasks can
  be regenerated indefinitely without scraping.
- **Downside** — the applications are realistic in *shape* but smaller and cleaner than
  production code. A model that does well here has demonstrated it can reason about an
  authorization boundary; it has not demonstrated it can do so inside a 500k-line
  monorepo.

Reference patches (`patched_files`) are also model-generated, then verified by execution.
They are not human-authored security review.

## Verification, not opinion

Nothing in this dataset was admitted on a model's or a human's judgement that code
"looks insecure." Each task passed four executable gates in an isolated sandbox:

1. The generated app boots and passes its own spec suite.
2. The exploit script fires against the vulnerable app (prints `PWNED`).
3. The reference patch stops the exploit from firing.
4. The patched app still passes the spec suite.

Candidates failing any gate were discarded rather than shipped. This is why the class
distribution below is uneven — it reflects which vulnerability classes survive automated
verification most reliably, not which classes matter most in the real world.

## Composition

1,000 tasks, merged from two generation batches (634 + 366) with zero duplicate ids.

| Vulnerability class | Tasks | Share |
|---|---:|---:|
| idor | 688 | 68.8% |
| missing_auth | 139 | 13.9% |
| mass_assignment | 92 | 9.2% |
| privilege_escalation | 35 | 3.5% |
| path_traversal | 31 | 3.1% |
| other | 9 | 0.9% |
| sql_injection | 6 | 0.6% |

All tasks: FastAPI / Python, ~2 files per application.

`sha256` of `dataset.jsonl`:
`7c1bbf2d1c1d507732f6109f39007c0803220d720c45f33b372a07c3f88f450d`

The IDOR concentration is the most important caveat in this release. A model can score
respectably here by learning one authorization pattern well. Read per-class results in
`results/leaderboard.json` rather than the headline number.

## Runtime environment

Tasks execute in ephemeral containers with **no network access at run time**. Dependencies
are pre-installed from a fixed set:

```
fastapi  uvicorn  requests  pydantic  sqlalchemy  pyjwt
passlib[bcrypt]  python-multipart  python-jose[cryptography]  httpx
```

This is why patches may not add dependencies — there is no way to install one. Models are
told this in the prompt, and a violation is recorded as a `requirements_changed` flag
rather than being scored as an insecure patch.

## Contamination

This dataset is public, so assume any model released after its publication may have seen
it. Treat VibeSec as an **open inspect set**: useful for understanding *how* a model fails
and for reproducing published numbers, not for certifying a newly released model.

Official ranking should use a held-out split that has never been published. If you are
evaluating your own model against these numbers, the honest comparison is against models
whose training cutoff predates this release.

## Reproducing the leaderboard

`results/eval_outcomes.jsonl` carries one row per `(model, task)`: the vulnerability
class, pass/fail, and the failure stage (`exploit_still_works`, `spec_broken`,
`parse_failed`, and so on). Aggregate it yourself with `python eval/merge_runs.py
--dry-run`; you should recover the table in `README.md` exactly.

Raw model responses and the patches each model produced are retained but not published
here, to keep the repository small. They are available on request.

## Task generation

The generator that produces and verifies these tasks is not part of this repository. The
verifier is — `exploit` and `spec_test` ship inside every task, so any score published
here can be independently reproduced without it.
